# 信息类插件：百胜战功、出框与胜率统计

两个独立插件均放在“信息”分类，使用核心统一分组、折叠、主题与插件管理。各自仅依赖核心及随包公共模块。

- “刷新战功”按需加载官方公共 `gn_gs_ahievement`、`character` 配置，然后调用现有 `AchievementManager.sendGetAchInfo(当前昵称, 0)`，这是向游戏服务器查询战功，不是云同步。安装但未挂载信息面板时不主动请求；0.1.4 起每次进入信息栏挂载面板时自动查询一次，进行中的查询合并。其他插件调用同一官方接口后，当前账号的完整回复也会立即刷新快照与已打开的面板，不额外补发查询。
- 仅接收 `requestType=0` 且昵称严格等于当前账号的完整战功回包，`type & 1` 为完成时间、`type & 2` 为条件进度。逐项相加 `CriteriaEntry.count` 和对应进度，不把所有定义硬编码为100次。
- 百胜定义使用 `flags=2048`；技能战功沿用 `flags=1024/1025` 或 `Id=1229`。直接显示“技能战功：状态”及下一行完整技能战功说明，长说明自动换行；补充表缺项时读取战功配置自身的name/desc。完成日期来自服务端完成时间。
- 默认“已拥有”；库存接口未就绪时保留归属未知条目并说明，不把未知当未拥有。未读取进度显示未知；本机快照显示时间，查询超时和消息缺口保留旧快照并提示刷新。
- 支持搜索、完成状态筛选和 JSON 导出。存储键为插件命名空间下的 `account:<ClientId>:snapshot-v1`，格式 `{schema:1,snapshot:{nickname,at,finish,progress}}`。

- 0.1.2起，导出采用中文字段（`格式版本:2`）：账号、带时区的导出/快照时间、全部与已拥有武将的完成汇总、逐武将百胜状态/进度/完成时间/条件及技能战功状态/条件。导出全部武将，不受面板筛选影响；未知归属、未知进度、未完成和完成时间未记录分别标明。已完成但不再返回条件计数时显示“已完成”，不显示误导的0/100。消息缺口等错误原文随报告保留。文件末尾保留原始快照及字段解释供排查；本机存储格式不变。

## 出框与胜率统计

插件ID仍为appearances，保留原有配置、折叠状态与本机出框。统计总览把每个武将的出框、选中、选取率、胜场、败场和胜率合在一张卡；对局历史将候选、选中、结果和时长合在同一局。共用模式、武将、时间、最低次数和排序筛选，斗地主分地主/农民，排位分先手（1、4号位）/后手（2、3号位），单骑分先手/后手；默认总览亦按模式与身份分别列出同一武将，各组独立计算出框率、选取率、胜率。顶部明确显示当前筛选合计。

| 类别 | 接受的客户端原生Model/Section | 排除 |
| --- | --- | --- |
| 排位 | 132/3 | 自由欢乐22、排位演武133/3、公会欢乐77/2及其他模式/分区 |
| 斗地主 | 148/3基础场、149/3高级场 | 赛事157/169、扑克牌175/47及其他模式/分区 |
| 单骑 | 160/2、160/3、160/4 | 明确识别为人机的对局；观战、回放、训练及其他模式 |

这些模式号来自本机客户端配套配置快照；已有原生模式/分区证据的本机行也需通过白名单才能进入统计。未验证的新模式或分区不自动纳入。新采集使用GameContext.GetModeType/GetGroupID及ClientSitdownRep.TypeID/GroupID；大厅标签不建立模式，原生35/44不作为旧归一标签解释。ClientTrainingRep及现存RoomControler.isTrainingGame veto训练。早期已保存记录缺少原始模式/分区时沿用其既有分类，不能追溯核实子模式，不补造证据。

单骑选将时读取两个座位及PlayerInfo的原生IsRobot/保护人机标记，结算再检查Players的isRobot/isProjectRobot。人机在结算才识别到时，同时移除该局临时出框并不保存战绩。没有完整标记时保持null，在总览和历史明确提示“人机身份未知”；未知记录保留，不按昵称、账号数值或对局耗时猜测。

- MsgGameDealCharacter Type1观察候选，Type3合并换将候选，逐局去重。SmsgGameSetCharacter只接受自己的座位确认；无法确认座位或选中武将不在候选内时舍弃当前草稿。确认后保存出框；进入游戏阶段可保存选取未知的候选。
- MsgGameOver只匹配当前观察对局，校验原始模式/分区、规则类型和自己座位；Players按SeatID定位，已有userId还需与当前账号相符。不能使用全局Result、对手结果或客户端SelfResult兜底（原客户端可能把Players[0]当作SelfResult）。重复结算只记一次。
- 自己的Result为0胜、1负、255平；其他或缺失保持未知。胜率＝胜场/(胜场+败场)，平局和未知不进入分母。每武将每局去重，时长来自官方结算time。出框率＝出现局数/已采集候选局数；选取率＝选中次数/选取结果已知的出框次数。
- 旧本机出框没有胜负，保留出框，不生成战绩或冒充败场。自己选将已观察但候选缺失时可仅记录战绩。不开历史查询请求，胜率从启用后的完整观察对局开始累积。
- 切号、停用、断线、重连、消息缺口舍弃未完成对局，已保存候选仍可保留为结果未知；配额失败保留待保存记录，可重试恢复。两类记录各10000条上限，满后暂停对应追加，不静默淘汰。

## 身份与先后手

- 选将确认与进入游戏阶段读取 GameContext.GetSeat(自己的SeatID).FixedViewId，作为一基行动号位保存到 position；不使用屏幕相对 ViewId，也不将零基协议 SeatID 直接加一。斗地主读取 Figure，结算以自己的 Players.Figure 补全。
- 依据本机缓存客户端 sgsGame_a.sgs：UpdateSeatFixedViewID 从 firstSeat/主公开始按存活可见座位编号；onFirstPhaseRole 根据服务器 SeatID 确定 firstSeat；单骑选将界面使用 GameContext.FirstHand，比较 FixedViewId。结算不再读取可能变化的原生座次。
- 同一武将跨模式、身份、先后手分别计算；出框率分母仅为本组已采集候选局数，未采到候选的结算只影响本组战绩。出框和战绩可通过同一局ID及相同模式的明确字段互相补齐；仍缺失身份/先后手的旧记录在加载时剔除并保存，恢复备份时同样过滤。不从旧 seat 字段猜测行动号位。
- position/figure 随本机记录、JSON导出和恢复保留，继续使用原schema。未知身份/先后手仅可作为内存草稿等待确认，不保存、不导出、不参与统计和历史；没有“未知”筛选入口。这里限定身份/先后手字段，未采集胜负、选取结果或人机标记的原有提示及规则不变。

本机键仍为account:<ClientId>:records-v1，schema仍为1，新增matches数组独立存储战绩；records保留原有出框。用户清空需二次确认并同时清空两类记录。卸载不删除数据。工具箱JSON导出包含format=sgs-toolbox-appearances-v1、schema、accountId、records、matches；恢复入口只接受该格式和当前账号，校验、去重与冲突检查后原子合并。

数据仅存本机，武将名称按需读取官方公共配置；无上传、云同步、外部胜率服务或账号历史查询。

## 账本

信息分类新增独立账本，最低核心0.5.38。包含重要物品余额、分别累计的登录收入/消耗、祈愿台次数与奖励，以及新页面的时间/物品筛选和具体日志；日志按账号保存在本机IndexedDB，无云同步。完整语义、协议依据及验证局限见[账本说明](ledger.md)。

排位候选读取：补采排位专用 MsgGameDealCharacterPaiwei.randomHt.get(自己SeatID).Datas 与正式排位 Type=9 候选；GsCFirstPhaseRole 到达后重新读取已更新的 FixedViewId，补交此前因号位未就绪暂存的出框。仍按原有正式模式白名单、账号、自己座位、重连和观战边界过滤。
