# 插件开发规范（契约 v1）

本文是本项目所有插件开发者的统一规范入口，适用于内置插件、独立插件和市场包。新增或改动插件前必须阅读；具体 API 查阅 [插件 API](plugin-api.md)，原生控件查阅 [原生主题接口](native-themes.md)。示例见 [可复制插件模板](../examples/plugin-template/index.js)。

“必须／禁止”是开发要求，“建议”是推荐做法。机器校验覆盖字段与部分资源边界，不能代替界面、业务行为和清理逻辑的检查。

公开投稿的环境准备、PR 内容、授权说明、CI 与合并后上架流程见 [贡献指南](../CONTRIBUTING.md)。该指南不替代本文契约；提交与合并源码本身不自动授权公共市场同步；审核服务实装并启用预先授权的试用区发布通道后，符合准入条件的社区版本按政策自动上架，无须逐包另行申请同步。

## 0. 开发流程与约束范围

本规范对仓库作者自己的插件、第三方插件及自动化开发一视同仁。不能以“内置”“演练里可用”或“历史代码”为理由跳过要求。源码、模板、校验器和 API 文档有冲突时，先查实际实现并修正冲突；不得悄悄降低校验、删掉失败断言或把兼容默认值当成新契约。

开始改动前，确认插件的稳定 ID、入口、最低核心、前置、设置默认值、数据归属和受影响界面；查阅对应功能说明与现有测试。新增插件同时登记 `tools/plugin-packages.mjs` 的发布入口和 `tools/plugin-quality.mjs` 的文档、功能测试及浏览器演练路径。目录、发布入口、验收索引必须一一对应；模板是唯一单列的非市场示例。

完成时必须留下可复核的结果：改了什么、为何改、实际运行的命令及结果、截图或报告位置、尚未验证的场景。检查失败必须修复，或在交付记录中保留失败原因与影响；有未解决失败时不能声称“全部符合”或“可发布”。不新增人工审批步骤。

| 检查层 | 可证明的内容 | 仍需人工或专项演练确认 |
| --- | --- | --- |
| `npm run check:plugins` | 全目录与发布／验收索引一致；严格清单、导出函数、完整依赖图；静态导入边界；受限环境加载冒烟；包大小、摘要及清单一致性 | 任意业务分支、完整无副作用性、最低核心是否与实际调用匹配、视觉质量 |
| `npm run check:plugin-lifecycle` | 全部正式插件在无登录环境、仅带声明前置时，安装、面板重复挂载与幂等清理、两轮启停、重载、测试升级、回退、卸载及注册资源释放；校验器拒绝错误样例 | 原生窗口、真实协议、持久化内容正确性、所有异步竞态、游戏强度或奖励到账 |
| 功能测试／浏览器与 Laya 演练 | 对应断言实际覆盖的功能、操作、主题和布局 | 未覆盖分支、官服协议时序、真实支付或扣款 |
| 官服实测 | 明确记录的版本、账号环境与操作结果 | 其他环境与历史记录；不得外推为全部场景已通过 |

`tools/plugin-quality.mjs` 是验收入口索引，检查文件存在不等于运行过测试；必须按改动范围执行。所有插件统一生命周期回归位于 `tests/plugin-lifecycle.test.js`，不维护只覆盖部分插件的手抄名单。

## 1. 清单、身份与兼容性

新源码必须声明完整清单，核心最低版本为 `0.5.0`：

```js
export const manifest = {
  id: 'example.local-info',
  name: '本地示例',
  version: '0.1.0',
  apiVersion: 1,
  contractVersion: 1,
  minCoreVersion: '0.5.0',
  description: '演示统一图标、主题配色和面板资源清理。',
  releaseNotes: '首次发布：提供跟随主题的只读示例面板。',
  icon: 'info',
  priority: 32768,
  categories: ['tools'],
};
```

| 字段 | 约定 |
| --- | --- |
| `id` | 稳定身份；1–64 个 ASCII 字符，以小写字母开头，其余仅小写字母、数字、点、短横线。不得通过更名重置用户配置或冒用其他插件。建议作者／项目使用独有前缀，如 `example.local-info`。 |
| `name` | 1–48 字符的非空单行展示名称，保持简短；不把版本、排序符号或广告塞入名称。 |
| `version` | `主版本.次版本.修订版本`，可附 `-预发布标识`；实际改动发布包时必须递增。插件与核心分别维护版本。 |
| `apiVersion` | 当前必须为数字 `1`，表示核心 API 代际。 |
| `contractVersion` | 当前必须为数字 `1`，表示遵守本规范的清单与面板契约。 |
| `minCoreVersion` | 最低可运行核心版本，使用无预发布后缀的 `x.y.z` 格式，各数字不得有多余前导零；本契约从 `0.5.0` 起提供。以后使用新接口时必须同步提高，不能仅因开发机运行正常就降低要求。 |
| `description` | 非空、单行、最多 160 字符的一句功能简介，不使用换行、HTML 或版本变更记录。完整帮助放在面板或文档。 |
| `releaseNotes` | 本版本最近一次更新内容，1–2000 字符非空纯文本，可分行；说明新增、修复与行为变化，不放完整历史或重复简介。兼容旧源码／旧包时允许省略，已发布包不得原版本补写；新插件与后续发布应填写真实内容。核心 0.6.33 起展示，旧核心可忽略，不因仅补展示元数据提高业务最低核心。 |
| `icon` | 公共图标名或本文定义的单色路径对象。 |
| `priority` | 数字整数 `0`–`65535`，越小越靠前；不接受字符串、小数或越界值。 |
| `dependencies` | 可选的前置插件 ID 数组，省略或 `[]` 表示无前置；不允许重复、自身依赖或循环依赖。使用时最低核心为 `0.5.62`。 |
| `categories` | 从下节分类中选取，不得重复；无界面插件声明 `[]`，且不注册面板。 |

`id` 是配置、折叠状态、安装记录与主题命名空间的关联键，应跨版本保持不变。不要用显示名称或插件版本作为持久化身份。确需更换身份时，应明确迁移策略并保留用户原有选择。

### 新源码与旧包

新插件及本仓库重新构建的插件必须通过严格契约校验；不能省略 `contractVersion` 来逃避要求。清单校验错误应在构建时修正。

核心仍兼容未声明 `contractVersion` 的已发布旧包。旧包缺少图标时使用 `package`，缺少插件排序值时使用 `32768`。这些是运行时兼容默认值，不是新源码的可选写法；旧包的哈希校验仍基于原始清单和代码，不能为补字段而改写已发布包。声明契约 v1 的包必须满足 v1 的全部要求；未知契约、无效字段或超过当前核心能力的最低版本不能默默降级运行。

## 2. 放在哪个面板

| 分类 | 用途 |
| --- | --- |
| `game` | 当前牌局／山河场景的信息与操作，例如卡牌记录、地图。 |
| `automation` | 已由用户配置启用的自动任务及其状态，例如日常领奖。 |
| `tools` | 手动工具、皮肤管理。 |
| `appearance` | 核心 0.6.18 起，外观配置面板；显示在管理的第三个“外观”页签，主题与卡牌工坊也位于此处。 |
| `manage` | 插件自己的维护设置或诊断入口；显示在核心管理内容之后，不替代核心安装、更新和回退操作。 |
| `info` | 使用帮助、说明、只读状态。 |

只声明实际需要的分类；后台插件使用 `categories: []`。不要为了曝光在多个分类重复同一面板。

```js
ctx.ui.registerPanel({
  id: 'main',
  category: 'tools',
  priority: 32768,
  render(container) {
    // 创建本面板内容，并在返回的函数中释放资源。
    return () => {};
  },
});
```

- `panel.id` 必须稳定、在同一插件内唯一；使用与插件 ID 相同的 1–64 字符规则，如 `main`、`history`。由核心补插件前缀，不手动添加其他插件 ID。
- `category` 必须存在于本插件 `manifest.categories`。只有一个分类时可省略并由核心补全；多分类插件必须明确填写。空分类数组不能注册面板。
- `render` 必须是函数。每次挂载只能操作给定容器及自己创建的界面，必须返回清理函数；该函数要能重复调用，并清理本次挂载创建的监听、订阅、样式、DOM 和原生资源。
- 可选 `title` 必须为 1–80 字符的非空单行文字；不需要时可省略，它不改变核心提供的插件组名称。
- `gameView` 仅可用于 `game`，取值为 `'battle'` 或 `'shanhe'`。未指定时为通用牌局面板；不需要视图筛选的插件不必填写。
- 核心统一提供插件图标、名称和整组折叠栏。不要再创建同名外层标题、整组折叠栏或私有导航；内容中的小节标题仍可使用。
- 折叠只隐藏界面，不停用插件、不改业务配置；切换分类导致面板重建时，必须释放上次挂载资源。不能把“当前不可见”当作“用户已停用”。

## 3. 排序规则

`manifest.priority` 决定同一分类中各插件组的顺序，也决定管理列表与市场列表的插件顺序。管理列表检测更新后，可更新插件优先置顶，组内仍遵循以下顺序。数字越小越靠前；同值按插件 `id` 的 ASCII 顺序稳定排列，不依赖安装时间、加载顺序或显示名称。市场同插件的多个版本最后按版本字符串稳定排列，此顺序不表示版本新旧或推荐程度。没有保留数字区间，各作者按功能需要填写；建议从 `32768` 开始，仅在确有理由时调整。

`panel.priority` 仅决定**同一插件组内**面板的顺序，取值同样为整数 `0`–`65535`，省略时为 `32768`；同值按局部 `panel.id` 稳定排列。它不能改变整个插件在分类中的位置，也不能把插件内容插到核心管理内容之前。

这两个优先级不控制执行顺序、权限、自动任务先后或主题覆盖层。`themes.override(tokens, priority)` 的覆盖顺序由主题 API 独立定义，不使用此处的 UI 排序约定。

## 4. 图标

优先使用公共线性图标，插件组图标由核心根据 `manifest.icon` 绘制；插件内部用 `ctx.ui.icon(nameOrSpec)` 获得独立 SVG 节点，再挂载到自己的按钮或内容中。

公共名称分为两组：

- 功能与状态：`cards`、`gift`、`effects`、`skins`、`palette`、`map`、`tools`、`toolbox`、`settings`、`info`、`package`、`automation`、`check`、`alert`。
- 操作：`refresh`、`reset`、`close`、`camera`、`expand`、`collapse`、`chevron`、`save`、`download`、`pointer`、`clipboard`、`share`、`play`、`pause`、`trash`、`update`。

另提供别名 `game → cards`、`manage → settings`、`reload → refresh`、`rollback → reset`。名称注册在 公共图标源文件 的 `ICON_NAMES`；新增公共名称时同步更新本文，只使用已公开名称，不能依赖未知名称的兼容回退。

`toolbox`、`expand`、`collapse`、`chevron` 从核心 `0.5.73` 起提供；插件清单或 `ctx.ui.icon()` 若使用这些新名称，需将最低核心版本设为 `0.5.73` 或以上。插件可复用 插件图标源文件 的身份图标，或在自己的清单中声明独立路径对象；以自包含的 `{paths}` 随清单发布，沿用旧版路径协议，不提高插件最低核心版本。新增插件应按功能选择独立轮廓；同一插件的面板标题、管理卡片、市场卡片和内部身份标题复用同一对象。播放、刷新等公共操作仍使用统一语义图标。

确无合适图标时可声明路径对象：

```js
icon: {
  paths: ['M4 5h16v14H4z', 'M8 9h8M8 13h5'],
}
```

对象只能含 `paths` 字段，数组至少 1 条、最多 8 条 SVG `d` 路径。每条最多 1024 字符，以 `M` 或 `m` 开始，只包含路径命令、数字及其分隔符。图标统一 `viewBox="0 0 24 24"`、单色线条、`stroke="currentColor"`，不依赖固定主题色。禁止传入 SVG/HTML 字符串、外链图片、数据 URL、额外 viewBox／颜色字段、事件属性、滤镜或脚本；不要在路径中夹带标签。

图标是辅助识别，不能代替操作语义。仅图标按钮必须有无障碍名称和悬停提示；语义不明确时保留短文字。装饰图标保持 `aria-hidden`，不要挤压按钮点击区域。

## 5. 主题与公共界面

工具箱拥有的 HTML、浮层和 Laya 原生控件都必须跟随当前主题，不仅是侧栏外框。HTML 使用 `--sgs-bg/surface/raised/text/muted/accent/border/danger/radius/font/motion`；核心 `0.5.15` 起，浅色主题通过 `tokens.scheme: 'light'` 声明（默认 `dark`），HTML 可用 `--sgs-scheme`；不要写死玄金或某一套主题的背景、正文和选中颜色。

优先使用 `ctx.ui.panel`、`ctx.ui.icon`、`ctx.ui.styleSwitch` 和 `ctx.ui.helpTip`。核心为注册面板注入公共样式。插件自建的 ShadowRoot 使用 `ctx.ui.mountStyles(root)`，并在浮层关闭时释放。支持早于该接口的核心时才随包携带必要的兼容控件。二态设置使用完全重绘的 `sgs-switch` 滑轨开关，互斥设置使用分段选择。禁止露出原生方形勾选框、圆点单选框或勾选框式列表。多选筛选使用选中底光、细侧线和文字状态。只读数据、普通操作、主操作和危险操作必须能清楚区分。

原生 Laya 控件使用 `ctx.ui.nativeTheme`：`bind` 绑定颜色，`watch` 立即绘制并订阅主题，`surface` 和 `chevron` 绘制统一表面。`surface` 只绘制一次，应在主题回调及状态变化时重绘；没有销毁的关闭面板也要调用释放函数。不要另建主题映射表、全局覆盖 Laya 原型或每个插件单独轮询主题。资源所有权与示例见 [原生主题接口](native-themes.md)。卡面、稀有度、明确业务警示等已有语义色可以保留，不应为统一皮肤而改变它们的含义。

插件名称、版本和单行简介保持清晰层级，长文本允许省略并能查看全文；错误详情必须能完整展开或复制。状态必须区分选中、部分选中、停用、加载、错误、零次数、无限和未知，不能只靠颜色表达。换主题与界面重绘不得修改用户配置、默认值或触发业务操作。

HTML 必须支持鼠标与键盘焦点／激活、明确的 `disabled` 状态和减少动画偏好。样式以插件命名空间限定，禁止写全局 `button`、`input` 等规则污染游戏或其他插件。拖动区域禁止选择文字；窄面板、长文本、低高度滚动和数字变化不得造成布局跳动。

纯主题包通过 `ctx.themes.register({id, name, description?, tokens})` 注册配色，清单使用 `categories: []`。核心提供主题工坊、预览与选择。注册示例、浅色与渐变字段见[主题接口](plugin-api.md#主题接口)。

### 布局与意外换行预防

后续新增或修改 UI 时必须检查以下成因并落实对应预防措施；核心、插件面板与浮层同样适用。

- **保留旧段落结构造成图标落单。** 将说明文字改为提示图标时，必须把提示与对应标题、标签、状态或操作放在同一行容器中；不能直接留在原独立段落位置。`inline-flex` 只控制控件内部布局，不能跨越相邻块级元素回到上一行。提示不应混入状态播报区域。
- **Flex 挤压与最小内容宽度。** 图标、提示按钮和开关应保留明确尺寸与不可压缩的点击区域；需要收缩的文字区域设置合理的 `min-width:0`。检查文字、图标、间距、内边距和边框的总宽度，不能只给文字加 `nowrap`，把换行变成溢出、遮挡或裁切。空间不足时须明确设计整组换行或上下排列，禁止提示图标单独落在下一行。
- **公共样式或继承影响尺寸。** 检查 `box-sizing`、`line-height`、按钮默认内边距、SVG 外边距及父级选择器；带文字按钮的图标间距不能直接套给纯图标按钮。优先使用公共控件，避免每处单独补丁。
- **字号与设备改变可用宽度。** 四档字号均须检查；考虑中文字体回退、浏览器文字自动放大、缩放与滚动条占宽。适用于移动端的界面须检查 iPad 横竖屏与分屏，适用于微端的界面须检查实际旧 Chromium 引擎，不能只改新版浏览器的 UA 就宣称覆盖微端兼容性。
- **内外宽度不一致导致漏检。** 模拟 248/280/420px 时必须确认外层宿主与内层面板的实际渲染宽度一致；字号调整、拖动缩放或历史内联宽度可能使内层仍保持较宽尺寸。不能只改宿主宽度，再以内部 `scrollWidth <= clientWidth` 判定通过；还须检查内层是否越过宿主边界。
- **把自然换行与布局错误混为一谈。** 短操作文字、提示与所属标签应保持预期组合；正文和错误详情允许自然换行且必须可完整查看。禁止对所有正文统一强制单行，也不能用隐藏溢出来掩盖错误。

交付前必须查看实际浏览器截图，覆盖适用的窄宽度、四档字号、长标题／简介、浅深主题与低高度滚动，并检查提示的鼠标、触屏及键盘操作。自动检查除横向溢出外，还应验证提示与对应文字的实际位置、按钮文字行数及点击区域；修改 Laya 原生布局时另用现有 Laya 演练检查。发现一个共用控件问题时须搜索同类使用位置，不能只修截图中的一个页面。记录实际环境、失败与未验证项，不将模拟结果写成实体设备或官服验收。

## 6. 生命周期与数据边界

- 模块顶层只声明清单、常量与函数，不启动计时器、下载、协议监听或游戏操作。副作用从 `activate(ctx)` 开始。
- `initialState` 和 `reduce` 必须保持纯计算。核心会为已安装但停用的插件继续处理本局事件，以保留记录；不能在 reducer 内发请求、写配置或执行业务动作。
- 所有监听、计时器、方法包装、DOM 和其他外部资源使用 `ctx.scope.listen/interval/timeout/patch/add` 登记。面板级资源还须在 `render` 返回的清理函数中及时释放，不能只等插件停用。
- 异步回调检查 `ctx.scope.signal.aborted`；支持取消的请求使用该 signal，面板重建还要检查本次挂载是否仍存活。插件停用、卸载或替换后不得继续轮询、写界面、发业务请求或恢复已清理的资源。
- 包装原生方法只作用于确认拥有的实例和必要方法，释放时不能覆盖其他代码后来写入的值；优先使用 `scope.patch`。不得为了发现控件不断扫描游戏对象或遍历任意 getter。
- 明确状态属于本局、当前账号、山河轮次还是插件设置。本局状态随核心 session 重置；账号切换后不得显示上一账号私有状态。未知、缺失、超限丢事件均保留“不确定”，不能伪装为零或完整记录。
- `ctx.settings/storage` 已按插件 ID 隔离，仍须为账号相关数据加入账号维度，明确存储格式与升级迁移。不要读取其他插件命名空间，或未经设计将牌局临时状态长期保存。
- 公共配置优先使用 `ctx.game.getConfigData/loadConfigData`；只读取所需字段，不拷贝完整登录对象或凭据。网络用途、目标与发送数据应可从源码和说明核对，不因打开面板隐式增加上传或外部服务依赖。
- 默认业务开关按现有功能约定保持，不因换肤、安装新版或 UI 整理自动启用。错误可短提示，但必须保留可查看的完整详情，不能吞掉错误或仅显示截断的一行。

### 自动操作与异步结果

- 定时检查、协议回调、按钮重复点击必须复用同一进行中任务或明确拒绝重复，不能重叠发送。重试须有次数或时间上限；超时表示结果未知，不能直接显示成功或盲目重复购买。
- 在发送前、每次 `await` 后及提交结果前核对作用域、当前账号和目标上下文。过期响应不得写入新账号、新一局或已关闭面板；原生窗口关闭后不得重新挂回旧节点。
- “已请求”“服务端确认”“资产到账”是不同状态。奖励、兑换、购买或充值成功必须依据对应响应／资产变化；证据不足保留等待、失败或未知，不能仅靠按钮点击或本地计数认定成功。
- 自动化遵循插件原有启用范围与用户排除项；新增付费、消耗道具、上传或外部服务用途必须说明触发条件、目标及数据。敏感信息不得进入诊断、导出、日志、URL 或公共市场包。
- 持久化结构升级要说明旧格式处理、账号隔离与失败恢复。清理运行资源不得顺手删除用户历史数据；显式清空操作应说明范围并提供必要的导出入口。

## 7. 独立构建、版本与迁移

每个插件必须自包含，无前置的插件可在仅启用自身时运行；声明 `dependencies` 的插件需要先安装并启用所有前置插件。声明前置只表达运行条件，不开放跨插件导入或状态访问。禁止跨插件目录导入、调用其他插件状态、依赖旧小抄随机全局或任意外部模块；公共代码只能来自明确的核心能力或随包打入的公共模块。不要通过把依赖写成动态访问来绕过构建检查。

源码只允许能静态打入包的相对 ESM 导入／再导出，所有传递依赖同样受检查。允许范围为本插件目录、`src/ui/`、`src/shared/`，及明确公开供打包使用的 `src/core/resources.js`（独立资源作用域）、`src/core/themes.js`（默认主题数据）、`src/core/seat.js`（座位投影辅助函数）。这些模块随包复制，不授权访问核心实例或另建核心服务。禁止导入其他核心内部模块、仓库外文件、裸包、Node 模块、HTTP 模块、`require` 或动态 `import()`；需要网络素材时使用相应资源 API，不下载并执行远程 JavaScript。新增共享模块先明确接口与所有权，不扩大整个核心目录的导入权限。

`npm run build` 在写入或清理任何构建产物前，对全部插件和模板执行同一套预检。预检先解析并校验整个导入图，再在无 DOM、网络和计时器的独立上下文执行模块加载冒烟（1500ms 上限，关闭字符串代码生成）。这能发现常见顶层副作用，不是恶意代码沙箱，也不能证明所有代码路径纯净；不得运行不可信包来代替源码审查。

旧包自动迁移只可匹配已核实的发布包精确哈希，禁止仅按 ID、版本或“看起来像旧包”替换。必须保留用户停用、卸载、回退和自定义包状态；迁移不能在用户回退后反复覆盖。失败时清理候选版本，维持可恢复的原有状态。

### 前置插件（核心 0.5.62）

例如盖主速刷声明 `dependencies: ['baisheng']`。核心先注册全部安装记录，再按依赖顺序激活。前置缺失、停用、启动失败或形成循环时，阻止依赖插件运行并展示完整原因，不自动安装或启用前置，不改变已有停用选择。核心 0.6.30 起，市场安装卡片可列出缺少的前置并询问“安装前置并继续”；仅在用户明确确认后，按依赖顺序安装市场最新正式版，再安装目标插件。已安装但停用或异常的前置仍需用户先启用或修复，不自动覆盖或启用。修复前置后可重试启用或重载依赖插件。

核心 `0.5.74` 起，更新或导入替换已安装的前置插件时，先完成下载、校验、编译和依赖循环检查，再从依赖链末端临时暂停已启用的直接及间接依赖插件。更新成功后按前置顺序重启这些插件；更新失败先恢复旧版本，再执行同样的恢复。临时暂停不写入停用设置、不清空本局状态；原已停用插件保持停用。单个依赖重启失败会保留完整错误，并继续恢复其他可运行的分支；核心关闭后不会重新启动。

暂停期间管理卡片显示“等待前置更新”或“正在恢复”，不误报运行异常；更新已提交但依赖恢复失败时会明确提示“已更新，但依赖插件重启失败”。停用、卸载、手动重载或回退前置插件仍需要先停用相关依赖。市场清单与构建依赖报告同步包含前置 ID。旧包未声明此字段时保持无前置语义；不会按插件 ID 或版本推断依赖或自动替换旧包。

## 8. 交付检查

1. 开发时执行 `npm run check:plugins` 与 `npm run check:plugin-lifecycle`；交付前执行 `npm run check:release`，顺序运行全量插件检查、完整 Node 回归及独立构建。修改分类、图标或排序接口时另执行 `npm run test:browser-plugin-contract`，按验收索引运行相关功能／浏览器测试。指定入口的 `check:plugins -- <入口>` 仅用于局部开发，不替代全仓检查。新模板不加入正式市场，也不通过篡改旧包获得示例包。
2. 单独启用插件，验证安装、停用、重新启用、重载、升级、回退与卸载；确认监听、定时器和原生包装不会累积，异常能恢复并查看详情。
3. UI 变化必须在实际浏览器渲染并查看截图，至少检查核心面板 `248/280/420px`，以及长标题、长简介、低高度滚动和浅／深背景；操作检查包含键盘和相关业务回归。
4. 切换各主题检查 HTML 和原生控件同步，打开中的面板立即更新；反复开关面板与停用插件后确认资源释放。原生控件使用项目现有 Laya 演练检查，保留原有业务语义。
5. 记录验证环境与局限：模拟浏览器、Laya 演练、官服实局是不同证据。只验证了模拟环境时不能写成官服验收通过。

推荐用 [交付记录模板](../examples/plugin-template/DELIVERY.md) 记录适用项。每项写“通过＋证据”“失败＋原因”或“不适用＋理由”；“未验证”必须保留为局限，不能打勾代替证据。API 最低版本、业务默认值、账号隔离、网络用途、主题、键盘、关闭后的异步取消及资源清理是每次评审的明确核对项。校验器本身变更必须包含错误样例回归，证明不合规代码确实被拒绝。

这些约定适用于人工和自动化开发，不新增额外审批步骤。实现与测试中发现规范和实际接口不一致时，应修正接口或文档并明确差异，不能让后续开发者依赖猜测。

### 插件用户文档

对照当前界面，用普通玩家能理解的语言说明插件用途、主要功能、打开位置、每个按钮／开关／筛选项和快捷操作。注明前置插件、必要限制、联网用途、可能上传的数据，以及自动操作、付费和游戏货币或道具消耗的触发条件。仅本机可见的效果也应说明。素材来源、作者和授权应保留。

用户说明不写更新历史、开发历史、逐版本记录、源码路径或代码实现。函数、类名、内部字段、协议、构建、校验和测试证据留在适用的开发者参考或交付记录中。本次发布的元数据仍按 `releaseNotes` 契约填写。

### 卡牌外观套装（核心 0.5.90）

使用 `ctx.cardStyles`，不自建加载器、原生方法包装或选择面板，不依赖记牌等插件。纯套装分类为 `[]`；颜色、命名空间与生命周期契约详见 [卡面与卡背接口](plugin-api.md#卡面与卡背)。

核心 0.5.117 起可声明逐牌图集 `atlas`，必须写明图片来源及索引／所有图片页的 HTTPS URL 和 SHA-256；只提供卡面无需附带卡背。核心只精确匹配原生牌名，未知特殊牌、资源缺失或失败回退原生，禁止用相近普通牌代替。完整限制见[逐牌图集接口](plugin-api.md#逐牌图集)。

核心 0.5.138 起，高清卡面可在 `atlas` 显式声明 `pixelRatio: 2` 或 `3`，同时提高插件最低核心至 0.5.138。省略为 1 倍，完整帧须严格对应 135×190 的该整数倍，不能借倍率字段放行其他布局。保留高清像素至 GPU，不修改原生逻辑尺寸。单页仍须满足 4096px / 8MiB、最多四页的限制。

**建议开发者自行选择存放卡面等大体积素材的位置**（对象存储、静态站点或 CDN），让素材与插件脚本分开发布，不把整套图片或 Base64 塞入插件包，也不默认依赖工具箱作者的存储空间。这是托管建议，不要求使用某家服务或向工具箱申请托管。图片须有可直接读取的 HTTPS 地址，允许游戏页面无凭据跨域 GET，避免登录、临时签名、重定向及第三方不稳定防盗链。

按不可变版本目录保存索引和图片，发布前生成真实文件 SHA-256；先上传并核对素材，再发布引用它们的插件包。不要覆盖已发布的同版本图片。声明来源、作者、生成方式和适用授权；站点代码的开源许可证不等于其中图片的授权。署名与授权示例见[大肥鱼卡面与卡背](dafeiyu-cards.md)。

核心 0.5.128：逐牌 atlas 的 index/pages 资源除 HTTPS 外，允许 HTTP 的本机 IPv4 回环地址 127.0.0.1（可带端口）。仍须声明并校验 SHA-256，不接受普通远程 HTTP、凭据或 URL 片段。本地卡面需保持素材服务运行；浏览器可能要求授予本地网络访问权限。图集格式及其他兼容字段见[逐牌图集接口](plugin-api.md#逐牌图集)。

核心 0.6.8 的 atlas.backImage 可提供 405×570 内嵌 PNG 卡背（最大 1 MiB），最低核心须同步提高。随包素材同样须记录来源、权利与验证证据；不得自动改变用户选择。

核心 0.6.185 起，内嵌卡背和卡面预览可使用 WebP，分别沿用 1 MiB 和 160 KiB 上限。使用时同步声明最低核心版本。重编码应保留尺寸和透明度，检查实际显示并核对体积收益。
